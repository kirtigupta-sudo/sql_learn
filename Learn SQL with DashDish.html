01 · The big picture

What is SQL?

SQL (Structured Query Language) is how we give instructions to a relational database. We use it to define tables, add and change records, find information, and control access.

Imagine DashDish needs to answer: “Which customers ordered from Portland restaurants last week?” The information is not stored in one giant spreadsheet. Customer details live in one table, restaurant details in another, and order events in a third. SQL lets us work with those tables together.

Tables, rows, and columns

A table stores one kind of thing. A table has columns describing that thing and rows representing individual records.

customer_idcustomer_namecityloyalty_tier
1Example customer APortlandgold
2Example customer BSeattlestandard

Here, customers is the table; customer_id, customer_name, city, and loyalty_tier are columns. Each horizontal record is a row. A unique ID lets us refer to one customer without relying on a name, which might change or be shared by two people.

Five common SQL command families

DDL · define structure

CREATE, ALTER, DROP

Build or change database objects such as schemas and tables. TRUNCATE and RENAME are also commonly taught with DDL.

DML · change records

INSERT, UPDATE, DELETE

Add, edit, or remove rows stored in tables.

DQL · read records

SELECT

Retrieve and analyze rows without changing the stored data.

TCL · control transactions

COMMIT, ROLLBACK, SAVEPOINT

Choose which data changes to keep or undo as a unit of work.

DCL · control permissions

GRANT, REVOKE

Decide which database actions a user or role is allowed to perform.

Classification note: some learning materials include SELECT under DML, while others use DQL as a separate category. The labels vary; the actions do not. In this course, DQL means “read data.”
How to read SQL: SQL keywords such as SELECT and FROM are usually written in uppercase for readability. Table and column names are often lowercase. SQL itself is generally case-insensitive for keywords, but strings such as 'Portland' are data and must be quoted.
02 · The case study

Meet DashDish

DashDish is a fictional food-delivery app. Its data model gives us enough variety to practice relationships, unmatched records, NULL values, totals, and ranking ties.

We will use six tables. Before querying, it helps to know what each table represents and how rows connect.

TableWhat one row meansLearning features
customersOne person who may place ordersIncludes a customer with no orders
restaurantsOne food businessIncludes a restaurant with no activity
couriersOne delivery workerIncludes an unassigned courier
menu_itemsOne item on a restaurant menuEqual ratings and one missing rating
ordersOne order eventMissing customer/courier IDs and a NULL courier
order_itemsOne product line within an orderMultiple lines per order; one missing item ID

How the tables relate

An order belongs to a customer and a restaurant. A courier may be assigned to deliver it. One order can contain several order lines, and each line refers to one menu item.

Think of the “one-to-many” relationship: one customer can place many orders; one order can have many order lines; one restaurant can offer many menu items. The ID in the “one” table is reused in the related “many” table. That repeated ID is what SQL uses to match records.
Why do some IDs have no match? We intentionally leave foreign keys off initially, so the sample data can demonstrate what joins do with missing matches. Later, we identify those orphan references and explain how foreign keys prevent them in production data.
03 · DDL · CREATE

Create the schema and tables

A database (also called a schema in MySQL) is a container for tables and other objects. First create the container, select it, then create each table inside it.

Create and select a schema

The first statement below deletes an existing DashDish database if one exists. This makes the setup repeatable, but it also permanently removes that database’s contents. Do not run it against a real database you need to keep.

DDL · schema setup · MySQL 8+
DROP DATABASE IF EXISTS dashdish;

CREATE DATABASE dashdish
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

USE dashdish;

CREATE DATABASE makes the container. CHARACTER SET utf8mb4 supports a broad range of text, including many international characters and symbols. The collation controls text comparison and sorting rules. USE dashdish makes this database the default location for later table commands.

Safe habit: check your selected database before running destructive statements. In a database client, use SELECT DATABASE(); to see the current one.

Choose column data types

A data type tells the database what kind of value a column stores and what operations make sense for it.

INT

Whole numbers, often used for IDs and counts.

VARCHAR(n)

Variable-length text, with a maximum length of n characters.

DATE / DATETIME

A calendar date, or a date with time-of-day information.

DECIMAL(p,s)

Exact decimal numbers. p is total digits and s is digits after the decimal point. Useful for prices.

BOOLEAN

True/false intent. In MySQL, BOOLEAN is a synonym for TINYINT(1).

NULL

Represents a missing or unknown value. It is not the same thing as zero or an empty string.

Create the reference tables

Start with customers, restaurants, and couriers. Each table has a primary key: a column (or set of columns) that uniquely identifies a row.

DDL · reference tables
CREATE TABLE customers (
  customer_id INT NOT NULL,
  customer_name VARCHAR(80) NOT NULL,
  city VARCHAR(60) NOT NULL,
  signup_date DATE NOT NULL,
  loyalty_tier VARCHAR(12) NOT NULL DEFAULT 'standard',
  PRIMARY KEY (customer_id)
);

CREATE TABLE restaurants (
  restaurant_id INT NOT NULL,
  restaurant_name VARCHAR(100) NOT NULL,
  cuisine VARCHAR(40) NOT NULL,
  city VARCHAR(60) NOT NULL,
  opened_on DATE,
  PRIMARY KEY (restaurant_id)
);

CREATE TABLE couriers (
  courier_id INT NOT NULL,
  courier_name VARCHAR(80) NOT NULL,
  vehicle_type VARCHAR(20) NOT NULL,
  home_city VARCHAR(60) NOT NULL,
  PRIMARY KEY (courier_id)
);

NOT NULL means the column must have a value on every row. DEFAULT 'standard' supplies a value when an insert leaves loyalty_tier out. opened_on is nullable because a restaurant’s opening date may not be known.

Create menus and order tables

Now define the tables that describe menu items, orders, and the line items inside orders. Notice that courier_id is nullable: an order can exist before a courier is assigned.

DDL · transactional tables
CREATE TABLE menu_items (
  item_id INT NOT NULL,
  restaurant_id INT NOT NULL,
  item_name VARCHAR(100) NOT NULL,
  category VARCHAR(30) NOT NULL,
  price DECIMAL(7,2) NOT NULL,
  rating DECIMAL(2,1),
  is_available BOOLEAN NOT NULL DEFAULT TRUE,
  PRIMARY KEY (item_id)
);

CREATE TABLE orders (
  order_id INT NOT NULL,
  customer_id INT NOT NULL,
  restaurant_id INT NOT NULL,
  courier_id INT,
  order_date DATETIME NOT NULL,
  status VARCHAR(20) NOT NULL,
  delivery_fee DECIMAL(6,2) NOT NULL DEFAULT 0,
  PRIMARY KEY (order_id)
);

CREATE TABLE order_items (
  order_item_id INT NOT NULL,
  order_id INT NOT NULL,
  item_id INT NOT NULL,
  quantity INT NOT NULL,
  unit_price DECIMAL(7,2) NOT NULL,
  PRIMARY KEY (order_item_id)
);

DECIMAL(7,2) allows up to seven digits total, two of them after the decimal point: for example, 12345.67. It is a better choice for currency than a floating-point type, which can store tiny binary rounding differences.

Why no foreign keys yet? We need invalid references for join demonstrations: for example, an order whose customer ID has no matching customer row. Real applications should usually enforce these relationships. We add them after studying the data and cleaning the examples.
04 · DDL · change structures

ALTER, DROP, TRUNCATE, and RENAME

Tables often evolve. A new business requirement might mean adding a column, widening a text field, or creating a constraint. DDL statements change database objects rather than simply editing a row.

ALTER TABLE: add a column

Suppose DashDish decides to store customer email addresses. ALTER TABLE ... ADD COLUMN changes the existing table structure.

DDL · add a nullable column
ALTER TABLE customers
ADD COLUMN email VARCHAR(255) NULL;

The new column allows NULL, so existing customer rows remain valid even though they have no email value yet. When a table already contains rows, a new NOT NULL column needs a safe plan—often a default value or a staged migration—because every existing row must receive a valid value.

Modify a column

To allow longer customer names, change the column’s type definition:

DDL · modify a column definition
ALTER TABLE customers
MODIFY COLUMN customer_name VARCHAR(120) NOT NULL;

In MySQL, MODIFY COLUMN requires you to write the full definition you want to keep, including NOT NULL. If you accidentally omit an existing property, you may change it. Before narrowing a type or changing nullability, inspect existing values to make sure they fit.

Rename a column

DDL · rename a column · MySQL 8
ALTER TABLE customers
RENAME COLUMN loyalty_tier TO membership_tier;

Renaming changes the column’s name, not its stored values. Any application query that still refers to loyalty_tier will need to be updated. Older MySQL versions commonly use CHANGE COLUMN old_name new_name definition, where the new type and constraints must also be specified.

DROP, TRUNCATE, and RENAME are not interchangeable

CommandWhat it removes/changesCan you filter rows?
DELETEDeletes selected row dataYes, with WHERE
TRUNCATE TABLEEmpties a table but keeps its structureNo
DROP TABLERemoves the table and its dataNo
RENAME TABLEChanges the table’s nameNot applicable

Here is a safe demonstration using a scratch table. It copies the structure of orders, copies rows into the scratch table, then empties, renames, and finally drops that temporary table.

DDL · scratch-table demonstration
CREATE TABLE scratch_orders LIKE orders;

INSERT INTO scratch_orders
SELECT * FROM orders;

TRUNCATE TABLE scratch_orders;

RENAME TABLE scratch_orders TO archived_orders;

DROP TABLE archived_orders;
Important MySQL behavior: DDL commonly causes an implicit commit, so it may not be undoable with a later ROLLBACK. TRUNCATE is DDL-like, cannot use a WHERE clause, and commonly resets an auto-increment counter. Always confirm the database and object name before destructive operations.
05 · Structure that protects data

Keys and constraints

A constraint is a rule the database checks when data is inserted or changed. Constraints are not just documentation: they reject values that violate the rule.

Primary keys

A primary key uniquely identifies each row. It must be unique and cannot be NULL. In our customers table, customer_id is the primary key. If two customers had the same ID, a query or relationship could no longer tell which row was intended.

Unique, NOT NULL, DEFAULT, and CHECK

  • UNIQUE prevents duplicate values in a column or group of columns.
  • NOT NULL requires a value.
  • DEFAULT supplies a value when an insert omits that column.
  • CHECK validates a condition, such as a nonnegative price.

Add check constraints to the menu table:

DDL · add constraints
ALTER TABLE menu_items
ADD CONSTRAINT chk_menu_price_nonnegative
CHECK (price >= 0);

ALTER TABLE menu_items
ADD CONSTRAINT chk_menu_rating_range
CHECK (rating IS NULL OR rating BETWEEN 0 AND 5);

The rating rule allows ratings from zero to five, and it also allows a missing rating. A check condition that evaluates to unknown because of NULL does not mean “rating is zero”; it means there is no rating value to validate.

Unique constraints and removing constraints

Once emails exist, we may want to prevent two customer accounts from using the same email. A unique constraint is appropriate only if the business rule truly says values must be unique.

DDL · unique constraint
ALTER TABLE customers
ADD CONSTRAINT uq_customer_email UNIQUE (email);

To remove a constraint in current MySQL, use its type-appropriate syntax:

DDL · remove constraints
ALTER TABLE menu_items
DROP CHECK chk_menu_rating_range;

ALTER TABLE customers
DROP INDEX uq_customer_email;

MySQL implements unique constraints using an index, so removing one is commonly done with DROP INDEX. Before adding a unique constraint to an existing table, search for duplicates; the alteration will fail if conflicting values already exist.

Foreign keys: protecting relationships

A foreign key ensures that a value in one table points to an existing row in another. For example, a valid order should normally refer to a real customer. The foreign key from orders.customer_id to customers.customer_id enforces that rule.

First find bad references:

DQL · find orphan references
SELECT o.order_id, o.customer_id
FROM orders AS o
LEFT JOIN customers AS c
  ON c.customer_id = o.customer_id
WHERE c.customer_id IS NULL;

SELECT oi.order_item_id, oi.item_id
FROM order_items AS oi
LEFT JOIN menu_items AS m
  ON m.item_id = oi.item_id
WHERE m.item_id IS NULL;

These queries reveal references with no parent row. In this teaching dataset, order 1015 uses a missing customer ID, and one order line references a missing menu item. Decide how to repair, quarantine, or remove those records before enforcing a foreign key.

Constraint timing matters: adding foreign keys immediately would prevent the intentionally unmatched examples from being loaded. In a production database, foreign keys are usually added as part of a planned schema migration after checking and cleaning existing rows.

After fixing the orphan values, the constraints would look like this:

DDL · add foreign keys after cleanup
ALTER TABLE orders
ADD CONSTRAINT fk_orders_customer
FOREIGN KEY (customer_id) REFERENCES customers(customer_id);

ALTER TABLE orders
ADD CONSTRAINT fk_orders_restaurant
FOREIGN KEY (restaurant_id) REFERENCES restaurants(restaurant_id);

ALTER TABLE orders
ADD CONSTRAINT fk_orders_courier
FOREIGN KEY (courier_id) REFERENCES couriers(courier_id);

ALTER TABLE order_items
ADD CONSTRAINT fk_order_items_order
FOREIGN KEY (order_id) REFERENCES orders(order_id);

ALTER TABLE order_items
ADD CONSTRAINT fk_order_items_menu
FOREIGN KEY (item_id) REFERENCES menu_items(item_id);

The courier key is nullable, so an order may have no courier yet. A non-NULL courier ID must still match a real courier. Foreign-key columns and referenced columns need compatible types. Decide explicitly what should happen when a referenced row is deleted: reject the deletion, cascade it, or set a nullable reference to NULL.

06 · Generated IDs

Manual IDs versus AUTO_INCREMENT

An ID is a stable label for a row. It does not have to communicate business meaning; its main job is to identify the record and connect related records.

Manually assigned IDs

Our case-study tables use manually assigned IDs. That means the insert statement provides each key:

DML · manual ID
INSERT INTO customers
  (customer_id, customer_name, city, signup_date)
VALUES
  (16, 'Sample customer', 'Portland', '2025-09-15');

This method makes the teaching data predictable: item 101 always refers to the same menu item in our examples. In real systems, manually coordinating IDs across multiple application servers can be inconvenient and may cause collisions.

Use AUTO_INCREMENT when MySQL should assign the ID

With AUTO_INCREMENT, MySQL generates a value if an insert leaves the ID column out. The column must be indexed, and it is most often the table’s primary key.

DDL + DML · generated IDs
CREATE TABLE app_customers (
  customer_id INT NOT NULL AUTO_INCREMENT,
  customer_name VARCHAR(80) NOT NULL,
  PRIMARY KEY (customer_id)
);

INSERT INTO app_customers (customer_name)
VALUES ('Sample customer one'), ('Sample customer two');

SELECT LAST_INSERT_ID();

Because customer_id is omitted from the insert’s column list, MySQL supplies the values. LAST_INSERT_ID() returns the first automatically generated ID from the most recent insert on the same connection.

Why not rely on “the next number”? Auto-increment values are identifiers, not a promise of gap-free numbering. Failed inserts, rollbacks, deletions, and concurrent operations can leave gaps. Do not use them as invoice numbers or assume they count the rows in the table.

You can explicitly insert a value into an auto-increment column, but doing so carelessly can affect what value is generated later. For application code, obtain the generated ID from the same database connection rather than guessing it.

08 · DML · change rows

INSERT, UPDATE, and DELETE

DML statements change records while leaving the table structure intact. The most important safety skill is checking which rows a statement will affect before changing or deleting them.

INSERT: add new rows

Use an explicit column list. It documents what each value means and protects you if a table’s column order changes later.

DML · INSERT
INSERT INTO menu_items
  (item_id, restaurant_id, item_name, category, price, rating, is_available)
VALUES
  (116, 1, 'Seasonal grain bowl', 'main', 14.25, 4.6, TRUE);

The columns and values correspond by position: item_id gets 116, restaurant_id gets 1, and so on. If you omit a column, it must either allow NULL, have a default, or be automatically generated; otherwise the insert fails.

UPDATE: change existing rows

Use WHERE to identify exactly which records should change. First run the filter as a SELECT to inspect the target rows.

DQL first · preview the target
SELECT item_id, item_name, price
FROM menu_items
WHERE restaurant_id = 1
  AND category = 'side';
DML · update selected rows
UPDATE menu_items
SET price = price * 1.05
WHERE restaurant_id = 1
  AND category = 'side';

This raises the matching side-item prices by five percent. The expression uses the current value on the right side of =. Without the WHERE clause, the update would change every row in menu_items.

DELETE: remove selected rows

DELETE removes rows, not the table definition. Again, preview the condition before running it:

DML · delete selected records
SELECT order_id, status, order_date
FROM orders
WHERE status = 'cancelled'
  AND order_date < '2025-01-01';

DELETE FROM orders
WHERE status = 'cancelled'
  AND order_date < '2025-01-01';

No rows in this sample meet that date condition, so the deletion affects zero rows. The example is intentionally cautious: it shows that an accurate condition matters more than the command itself.

Beginner safety rule: never run an unfamiliar UPDATE or DELETE without a WHERE clause. When you do need to change many rows, use a transaction where possible, inspect the affected-row count, and keep a backup or recovery plan.
09 · DQL · read data

SELECT, columns, and filtering

A SELECT query asks the database to return a result set. A result set looks like a temporary table: it has columns and rows, but a normal query does not change the source data.

Choose which columns to return

DQL · select all columns
SELECT *
FROM customers;

The asterisk means “all columns.” It is handy while exploring a table, but it can return unnecessary data and make a query fragile if columns are added later. For reusable queries, list only the fields you need.

DQL · select chosen columns
SELECT customer_id, customer_name, city
FROM customers;

Calculate and name a result column

A query can calculate values while reading data. AS gives the calculated expression a readable label.

DQL · expression and alias
SELECT
  item_name,
  price,
  price * 1.10 AS example_price_after_10_percent
FROM menu_items;

The expression multiplies each price by 1.10. The alias names the result column; it does not create a new stored column. This is only an arithmetic demonstration, not a statement about the applicable tax rate.

WHERE: keep rows that meet a condition

WHERE is a row filter. The database checks each row against the condition and includes rows for which the condition is true.

DQL · comparison and AND
SELECT item_name, price, rating
FROM menu_items
WHERE price > 10
  AND is_available = TRUE;

The query requires both conditions: the price must be greater than 10, and the item must be available. Comparison operators include =, <> (not equal), <, <=, >, and >=.

Combine conditions and use parentheses

DQL · AND, OR, parentheses
SELECT customer_name, city, loyalty_tier
FROM customers
WHERE (city = 'Portland' OR city = 'Seattle')
  AND loyalty_tier <> 'standard';

Parentheses mean “first decide whether the city is Portland or Seattle; then require the tier not to be standard.” Without parentheses, SQL’s operator precedence can produce a different result than the one a person intended. Make logic explicit rather than relying on memory of precedence.

BETWEEN, IN, and LIKE

DQL · common filters
SELECT item_name, category, price
FROM menu_items
WHERE price BETWEEN 8 AND 15
  AND category IN ('main', 'side');

SELECT restaurant_name
FROM restaurants
WHERE restaurant_name LIKE 'C%';
  • BETWEEN 8 AND 15 includes both endpoints: 8 and 15.
  • IN (...) is a shorter way to compare a value against several choices.
  • LIKE 'C%' finds text beginning with C. % matches any number of characters; _ matches one character.

ORDER BY and LIMIT

Tables do not promise a particular order. Use ORDER BY when order matters. LIMIT is useful for previews or top-N lists.

DQL · sort and limit
SELECT item_name, price
FROM menu_items
ORDER BY price DESC, item_name ASC
LIMIT 5;

DESC sorts from high to low; ASC sorts from low to high and is the default. Here, price is sorted high-to-low, and tied prices are sorted by item name. Adding a tie-breaker makes output more predictable.

10 · Missing values and logic

NULL, CASE, and SQL’s three-valued logic

NULL means “missing, unknown, or not recorded.” It is not a normal value, so you must use special tests and understand how it affects calculations.

Why = NULL does not work

Comparisons with NULL do not produce true or false in the usual way. The result is “unknown.” Use IS NULL or IS NOT NULL.

DQL · find missing values
SELECT order_id, courier_id
FROM orders
WHERE courier_id IS NULL;

SELECT item_name, rating
FROM menu_items
WHERE rating IS NOT NULL;

The first query finds an order without an assigned courier. The second finds only items with a recorded rating. Do not write courier_id = NULL; it will not find the missing value.

COALESCE: choose a fallback for display

COALESCE returns the first non-NULL value in its argument list. It is useful for presentation, but the fallback should not be confused with real stored data.

DQL · display a fallback
SELECT
  order_id,
  COALESCE(CAST(courier_id AS CHAR), 'Not assigned') AS courier
FROM orders;

The ID is converted to text so the result can display either a number or a phrase. The original courier_id remains NULL; this query changes only the output.

CASE: create categories from conditions

CASE is SQL’s conditional expression. It checks conditions from top to bottom and returns the value for the first matching branch.

DQL · CASE expression
SELECT
  order_id,
  delivery_fee,
  CASE
    WHEN delivery_fee = 0 THEN 'Free'
    WHEN delivery_fee < 3 THEN 'Low'
    ELSE 'Standard'
  END AS fee_band
FROM orders;

Order matters: a zero fee also satisfies “less than 3,” so the zero-fee test must come first. If no WHEN condition matches and there is no ELSE, the result is NULL.

11 · Summarize rows

Aggregate functions, GROUP BY, and HAVING

An aggregate function summarizes several rows into one value. Instead of seeing each menu item, you can ask for an average price, number of items, or highest rating.

Common aggregate functions

DQL · aggregate summary
SELECT
  COUNT(*) AS item_rows,
  COUNT(rating) AS rated_items,
  COUNT(DISTINCT category) AS distinct_categories,
  AVG(price) AS average_price,
  MIN(price) AS lowest_price,
  MAX(price) AS highest_price,
  SUM(price) AS sum_of_menu_prices
FROM menu_items;
  • COUNT(*) counts rows.
  • COUNT(rating) counts only rows where rating is not NULL.
  • COUNT(DISTINCT category) counts different non-NULL category values.
  • AVG, MIN, MAX, and SUM summarize numeric values.
Choose the right meaning: adding every menu-item price does not calculate sales. To calculate sales, use order-line quantities multiplied by the recorded unit prices. The table’s grain—the kind of thing one row represents—determines what an aggregate means.

GROUP BY: summarize each group separately

Without GROUP BY, the query above returns one summary for the entire table. With GROUP BY, SQL divides rows into groups and calculates an aggregate per group.

DQL · group menu items per restaurant
SELECT
  restaurant_id,
  COUNT(*) AS item_count,
  AVG(price) AS average_price
FROM menu_items
GROUP BY restaurant_id
ORDER BY average_price DESC;

All items with the same restaurant_id form a group. The output contains one row per restaurant that has a menu item. Restaurant 15 does not appear, because this query starts from menu_items, and it has no item rows.

WHERE versus HAVING

WHERE filters individual rows before grouping. HAVING filters completed groups, often using an aggregate. For example, “only restaurants with at least two menu items” is a group-level condition.

DQL · filter groups
SELECT
  restaurant_id,
  COUNT(*) AS item_count,
  AVG(price) AS average_price
FROM menu_items
WHERE is_available = TRUE
GROUP BY restaurant_id
HAVING COUNT(*) >= 2
ORDER BY item_count DESC;

The database first removes unavailable items, then groups the remaining rows by restaurant, then keeps groups with two or more rows. Filtering order changes the answer, so decide whether your condition applies to rows or groups.

Conditional aggregation

Conditional aggregation calculates several related measures in one pass. Put a CASE inside SUM or COUNT.

DQL · order counts by status
SELECT
  restaurant_id,
  COUNT(*) AS all_orders,
  SUM(CASE WHEN status = 'delivered' THEN 1 ELSE 0 END) AS delivered,
  SUM(CASE WHEN status = 'cancelled' THEN 1 ELSE 0 END) AS cancelled
FROM orders
GROUP BY restaurant_id;

For each order, the delivered expression returns 1 if delivered and 0 otherwise. Summing those ones and zeros counts delivered orders. Strict SQL requires selected expressions to be grouped or aggregated; MySQL’s ONLY_FULL_GROUP_BY mode helps detect ambiguous queries.

12 · Combine related tables

Joins: connect rows using IDs

A join combines rows from two tables based on a matching condition. Use joins when the answer needs facts stored in more than one table—for example, an order status plus the customer’s name.

INNER JOIN: keep matches only

JOIN by itself means INNER JOIN in MySQL. A row appears only when the join condition finds a matching row on both sides.

DQL · orders with customer and restaurant
SELECT
  o.order_id,
  c.customer_name,
  r.restaurant_name,
  o.status
FROM orders AS o
JOIN customers AS c
  ON c.customer_id = o.customer_id
JOIN restaurants AS r
  ON r.restaurant_id = o.restaurant_id
ORDER BY o.order_id;

o, c, and r are table aliases—short names used in the query. The ON clauses tell SQL how to match rows. Order 1015 is absent because it has no matching customer. The inner join does not invent a placeholder customer.

LEFT JOIN: keep every row from the left table

A left join preserves all rows from the table on the left side. If there is no right-side match, the right-side columns appear as NULL. This is useful for finding customers who have never ordered.

DQL · find customers with no orders
SELECT c.customer_id, c.customer_name
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;

Customer 15 appears because that customer has no order. The unmatched order 1015 does not cause an extra customer to appear, because the query preserves customers, not orders.

RIGHT JOIN, FULL OUTER JOIN, and CROSS JOIN

  • RIGHT JOIN keeps every row from the right table and matches from the left. It can usually be rewritten as a LEFT JOIN by swapping table order.
  • FULL OUTER JOIN keeps matched rows and unmatched rows from both sides. MySQL does not support native FULL OUTER JOIN syntax; a common workaround combines left-join results with UNION ALL and filters the unmatched half.
  • CROSS JOIN pairs every left row with every right row. Fifteen customers crossed with fifteen restaurants produces 225 pairs.
DQL · all customer/restaurant combinations
SELECT c.customer_name, r.restaurant_name
FROM customers AS c
CROSS JOIN restaurants AS r;

A cross join can be useful for generating all possible combinations, but row counts multiply. A careless cross join on large tables can create a huge result.

Full-join behavior in MySQL

To see matches and unmatched rows from both customers and orders, use a left join in each direction and append the unmatched orders:

DQL · emulate full outer join
SELECT
  c.customer_id,
  c.customer_name,
  o.order_id
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.customer_id

UNION ALL

SELECT
  c.customer_id,
  c.customer_name,
  o.order_id
FROM orders AS o
LEFT JOIN customers AS c
  ON c.customer_id = o.customer_id
WHERE c.customer_id IS NULL;

The first half includes every customer and any matching orders. The second adds only orders that had no matching customer. UNION ALL preserves rows; unlike UNION, it does not remove duplicates. Both query parts need the same number of columns in compatible positions.

Join at the correct grain

The word grain means what one row represents. An order table has one row per order; an order-items table has one row per product line. Joining them produces one row per order line, so an order with two lines appears twice.

DQL · order lines with menu details
SELECT
  o.order_id,
  oi.order_item_id,
  mi.item_name,
  oi.quantity,
  oi.unit_price
FROM orders AS o
JOIN order_items AS oi
  ON oi.order_id = o.order_id
LEFT JOIN menu_items AS mi
  ON mi.item_id = oi.item_id
ORDER BY o.order_id, oi.order_item_id;

The left join to menu items preserves the line with the invalid menu ID, but its item_name is NULL. If we used an inner join there, that line would disappear from the results.

Common total bug: if you join an order-level delivery fee to order lines, the fee repeats once per line. Summing it after that join can overcount delivery fees. Calculate line totals at line grain, aggregate them to one row per order, and only then add the fee.

Self joins

A self join joins a table to itself. It is useful when rows in the same table are related to each other. For example, an employee table might contain both an employee ID and a manager ID. Aliases are essential because SQL needs to distinguish the two roles played by the same table.

13 · Queries inside queries

Subqueries and CTEs

Sometimes one query needs the result of another query. A subquery or common table expression (CTE) lets you express the smaller calculation and use its result in a larger query.

Scalar subquery: one value

A scalar subquery returns one value. Here the inner query calculates the average menu price; the outer query finds items priced above that average.

DQL · scalar subquery
SELECT item_name, price
FROM menu_items
WHERE price > (
  SELECT AVG(price)
  FROM menu_items
);

The inner query runs as part of the larger statement. It must return exactly one value in this comparison. If a scalar subquery accidentally returns multiple rows, SQL reports an error.

IN and EXISTS

IN checks whether a value appears in a set. EXISTS checks whether a related query returns at least one row.

DQL · customers who have placed orders
SELECT customer_id, customer_name
FROM customers
WHERE customer_id IN (
  SELECT customer_id
  FROM orders
);

SELECT c.customer_id, c.customer_name
FROM customers AS c
WHERE EXISTS (
  SELECT 1
  FROM orders AS o
  WHERE o.customer_id = c.customer_id
);

The second query is correlated: its inner query refers to the current outer customer. EXISTS returns true as soon as at least one matching order exists. The 1 is a conventional placeholder; the actual selected value is not important to the existence test.

NULL and NOT IN: if a NOT IN subquery includes NULL, the result may surprise you because comparisons become unknown. For “does not have a matching row,” NOT EXISTS is often safer.

CTEs: name the steps in a query

A common table expression begins with WITH. It gives a temporary result a name so a complex query can be organized into readable steps. The CTE exists only for the statement immediately following it.

DQL · CTEs for order totals and customer spend
WITH order_food_totals AS (
  SELECT
    order_id,
    SUM(quantity * unit_price) AS food_total
  FROM order_items
  GROUP BY order_id
),
customer_totals AS (
  SELECT
    o.customer_id,
    COUNT(*) AS order_count,
    SUM(t.food_total + o.delivery_fee) AS spend
  FROM orders AS o
  JOIN order_food_totals AS t
    ON t.order_id = o.order_id
  GROUP BY o.customer_id
)
SELECT
  c.customer_name,
  ct.order_count,
  ct.spend
FROM customer_totals AS ct
JOIN customers AS c
  ON c.customer_id = ct.customer_id
ORDER BY ct.spend DESC;

Read the query in layers:

  1. order_food_totals calculates each order’s food subtotal from its line items.
  2. customer_totals adds the delivery fee and summarizes order count and spend per customer.
  3. The final query attaches customer names and sorts by spending.

CTEs can make a query easier to understand, but they are not automatically faster than subqueries. The database optimizer still decides how to execute the statement.

Recursive CTE

A recursive CTE refers to itself. It can generate sequences, walk hierarchical data, or follow paths. It has an initial row (the anchor) and a recursive part that adds rows until a stop condition is met.

DQL · generate a date sequence
WITH RECURSIVE days AS (
  SELECT DATE('2025-09-01') AS day

  UNION ALL

  SELECT day + INTERVAL 1 DAY
  FROM days
  WHERE day < '2025-09-07'
)
SELECT day
FROM days;

The first select starts at September 1. Each recursive step adds one day. The WHERE condition stops the recursion at September 7. Always design a termination condition; a recursive query that does not stop can run into recursion limits or consume unnecessary resources.

14 · Analyze rows without collapsing them

Window functions

A window function calculates across a related set of rows but keeps each individual row in the output. That is the key difference from GROUP BY, which collapses each group into a single result row.

ROW_NUMBER, RANK, and DENSE_RANK

These functions assign rankings. Their behavior differs when two menu items have the same rating.

DQL · compare ranking functions
SELECT
  item_name,
  rating,
  ROW_NUMBER() OVER (
    ORDER BY rating DESC, item_id
  ) AS row_num,
  RANK() OVER (
    ORDER BY rating DESC
  ) AS rating_rank,
  DENSE_RANK() OVER (
    ORDER BY rating DESC
  ) AS dense_rank
FROM menu_items
WHERE rating IS NOT NULL
ORDER BY rating DESC, item_id;
Ratings in descending orderROW_NUMBER exampleRANKDENSE_RANK
4.9, 4.91, 21, 11, 1
4.8, 4.83, 43, 32, 2
4.7, 4.75, 65, 53, 3

ROW_NUMBER gives each row a different number. We add item_id as a tie-breaker so the order is repeatable. RANK gives tied values the same rank and leaves a gap afterward. DENSE_RANK gives tied values the same rank but does not leave a gap.

PARTITION BY: restart within groups

PARTITION BY divides the rows into independent groups before calculating a window function. It is similar to grouping for the calculation, but it does not collapse the rows.

DQL · rank menu items per restaurant
SELECT
  restaurant_id,
  item_name,
  rating,
  DENSE_RANK() OVER (
    PARTITION BY restaurant_id
    ORDER BY rating DESC
  ) AS restaurant_rating_rank
FROM menu_items
WHERE rating IS NOT NULL
ORDER BY restaurant_id, restaurant_rating_rank;

The ranking starts again for every restaurant. Without PARTITION BY restaurant_id, all items compete in one overall ranking.

Running totals and LAG

Window frames define exactly which nearby rows contribute to a windowed aggregate. ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW means “from the first row in this customer’s ordered history through the current row.”

DQL · running customer spend and previous order
WITH order_totals AS (
  SELECT
    o.order_id,
    o.customer_id,
    o.order_date,
    SUM(oi.quantity * oi.unit_price) + o.delivery_fee AS total
  FROM orders AS o
  JOIN order_items AS oi
    ON oi.order_id = o.order_id
  GROUP BY
    o.order_id,
    o.customer_id,
    o.order_date,
    o.delivery_fee
)
SELECT
  customer_id,
  order_id,
  order_date,
  total,
  SUM(total) OVER (
    PARTITION BY customer_id
    ORDER BY order_date, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS running_spend,
  LAG(total) OVER (
    PARTITION BY customer_id
    ORDER BY order_date, order_id
  ) AS previous_order_total
FROM order_totals
ORDER BY customer_id, order_date;

LAG(total) looks at the prior row in the ordered window. The earliest order per customer has no prior order, so the result is NULL. LEAD looks forward instead. The order total is assembled from line items and the order fee; the query’s grouping ensures one row per order before applying the window functions.

15 · TCL · protect changes

Transactions, COMMIT, ROLLBACK, SAVEPOINT

A transaction groups database changes into one unit of work. It gives you a chance to review changes before making them permanent, and it can undo uncommitted data modifications.

Transaction basics

In MySQL, begin a transaction with START TRANSACTION. Use COMMIT to keep changes, or ROLLBACK to undo uncommitted transactional changes. For this to work as expected, the tables must use a transactional storage engine such as InnoDB.

TCL + DML · preview, then commit
START TRANSACTION;

UPDATE menu_items
SET price = price * 0.95
WHERE restaurant_id = 1;

SELECT item_id, item_name, price
FROM menu_items
WHERE restaurant_id = 1;

COMMIT;

While the transaction is open, inspect the result. If it is correct, commit. If not, issue ROLLBACK instead. The exact visibility of uncommitted changes to other sessions depends on the isolation level.

SAVEPOINT: undo only later work

A savepoint marks a position inside a transaction. You can roll back to that marker while keeping changes made before it.

TCL · partial rollback
START TRANSACTION;

UPDATE menu_items
SET price = price * 0.95
WHERE restaurant_id = 1;

SAVEPOINT after_discount;

UPDATE orders
SET delivery_fee = 0
WHERE status = 'delivered';

ROLLBACK TO SAVEPOINT after_discount;

COMMIT;

The menu price change happened before the savepoint, so it remains. The delivery-fee update happened after it, so it is undone. The final commit preserves the price update.

ACID properties

Atomicity

A transaction’s work is treated as one unit: commit it or undo uncommitted changes.

Consistency

Valid constraints and rules remain satisfied as the database moves from one valid state to another.

Isolation

Concurrent transactions are controlled so one task does not see an unsafe mixture of another task’s intermediate work.

Durability

After a successful commit, the database is responsible for preserving the committed result.

DDL caveat in MySQL: statements such as CREATE TABLE, ALTER TABLE, and TRUNCATE often cause an implicit commit. Do not assume a transaction can roll back a schema change.
16 · DCL · control access

GRANT and REVOKE

Database permissions determine which actions an account may perform. A reader might be allowed to run SELECT but not change or delete data.

MySQL accounts include both a user name and a host component. For example, 'dashdish_reader'@'localhost' is not necessarily the same account as 'dashdish_reader'@'%'.

DCL · create a read-only account and grant access
CREATE USER 'dashdish_reader'@'localhost'
IDENTIFIED BY 'Use-a-unique-secret-from-a-secret-manager';

GRANT SELECT ON dashdish.*
TO 'dashdish_reader'@'localhost';

SHOW GRANTS FOR 'dashdish_reader'@'localhost';

REVOKE SELECT ON dashdish.*
FROM 'dashdish_reader'@'localhost';

GRANT SELECT allows the account to read tables in dashdish. REVOKE removes that privilege. The password shown is instructional text, not a credential to reuse. In real deployments, use a secret manager and follow your organization’s account-creation practices.

Least privilege: grant only the permissions the account needs. A reporting account usually should not be able to delete customer data or change database structure.
17 · Query performance

Indexes and EXPLAIN

An index is an additional data structure that helps the database find rows more efficiently. It is similar to the index at the back of a book: instead of scanning every page, you can look up where a topic appears.

Create useful indexes

DDL · indexes for common access patterns
CREATE INDEX idx_orders_customer_date
ON orders (customer_id, order_date);

CREATE INDEX idx_orders_restaurant_status
ON orders (restaurant_id, status);

CREATE INDEX idx_menu_restaurant_rating
ON menu_items (restaurant_id, rating);

The best indexes depend on how queries search, join, and sort. Composite indexes have an order: an index on (customer_id, order_date) is most useful when a query filters by customer_id or by both columns. It generally is not equivalent to having a separate index on order_date.

Indexes have a cost: they use storage, and inserts or updates may take longer because indexes must also be maintained. Adding an index to every column is not a good strategy. Measure actual workloads and query plans.

EXPLAIN: inspect the planned work

EXPLAIN shows how MySQL plans to execute a query. It can reveal whether the optimizer expects to use an index or scan many rows.

DQL · inspect a query plan
EXPLAIN
SELECT order_id, order_date
FROM orders
WHERE customer_id = 3
ORDER BY order_date;

Look at the plan as diagnostic information, not a pass/fail grade. A table scan can be reasonable for a tiny table. MySQL 8 also supports EXPLAIN ANALYZE, which executes the statement and reports actual timing and row counts:

DQL · execute and analyze
EXPLAIN ANALYZE
SELECT order_id, order_date
FROM orders
WHERE customer_id = 3
ORDER BY order_date;
Use care: because EXPLAIN ANALYZE runs the query, do not casually use it on an expensive statement against production-sized data.
18 · Practice lab

Practice by asking business questions

Try each prompt before opening its solution. Read the query, predict what it returns, and then run it in a MySQL environment with the DashDish dataset.

Challenge 1: Find customers who have never ordered

Return each customer’s ID and name when no matching row exists in orders.

Show a solution
DQL · anti-join pattern
SELECT c.customer_id, c.customer_name
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;

The left join preserves customers without matches. For those customers, o.order_id is NULL, so the filter keeps only the unmatched rows.

Challenge 2: Count delivered orders for every restaurant

Include restaurants with zero delivered orders. Show the restaurant name and its delivered-order count.

Show a solution
DQL · LEFT JOIN with aggregate
SELECT
  r.restaurant_name,
  COUNT(o.order_id) AS delivered_orders
FROM restaurants AS r
LEFT JOIN orders AS o
  ON o.restaurant_id = r.restaurant_id
 AND o.status = 'delivered'
GROUP BY r.restaurant_id, r.restaurant_name
ORDER BY delivered_orders DESC;

The status test belongs in ON, so restaurants are preserved even if they have no delivered orders. COUNT(o.order_id) counts matched order IDs and returns zero for an unmatched restaurant. COUNT(*) would count the preserved restaurant row and misleadingly return one.

Challenge 3: Show the top two distinct ratings per restaurant

Use a window function and include tied ratings at the cutoff.

Show a solution
DQL · DENSE_RANK and CTE
WITH ranked AS (
  SELECT
    restaurant_id,
    item_name,
    rating,
    DENSE_RANK() OVER (
      PARTITION BY restaurant_id
      ORDER BY rating DESC
    ) AS rnk
  FROM menu_items
  WHERE rating IS NOT NULL
)
SELECT restaurant_id, item_name, rating, rnk
FROM ranked
WHERE rnk <= 2
ORDER BY restaurant_id, rnk, item_name;

The CTE calculates rank for each menu item within its restaurant. Because it uses DENSE_RANK, all items with the top two distinct rating values are included, including ties.
